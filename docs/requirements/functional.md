# Функциональные требования

Статус: **черновик**, согласование с заказчиком 27.10.2026. Заменяют 13 требований спринта 1: продукт теперь — расширение Zabbix ([D-004](../architecture/decisions.md)).

Приоритет: **MVP** — обязательно к защите; **Если успеем** — после MVP, по порядку из [дорожной карты](../product/roadmap.md).

## MVP

| ID | Требование | Спринт |
|---|---|---|
| FR-01 | Система должна обеспечивать получение в реальном времени событий Zabbix о возникновении и закрытии проблем через коннектор. | 2 |
| FR-02 | Система должна обеспечивать получение из Zabbix через API истории метрик и записей логов наблюдаемых сервисов за заданный интервал времени. | 2 |
| FR-03 | Система должна обеспечивать построение карты связей сервисов («кто кого вызывает») по тегам хостов Zabbix. | 2 |
| FR-04 | Система должна обеспечивать объединение проблем, возникших в близком окне времени на связанных сервисах, в один инцидент. | 2 |
| FR-05 | Система должна обеспечивать формирование для инцидента ранжированного списка подозреваемых сервисов по тому, какой сервис раньше других отклонился от своей нормы. | 3 |
| FR-06 | Система должна обеспечивать подбор доказательств к инциденту: отклонившихся метрик и характерных записей логов вокруг начала инцидента. | 3 |
| FR-07 | Система должна обеспечивать публикацию разбора инцидента комментарием к проблеме в Zabbix с указанием вероятного источника, доказательств и ссылок на графики. | 2–3 |
| FR-08 | Система должна обеспечивать отправку оповещения с разбором в Telegram ответственной команде, определённой по справочнику «сервис — команда». | 2–3 |
| FR-09 | Система должна обеспечивать приём разметки сбоев от тестового стенда и расчёт точности разбора: доли инцидентов, где источник назван первым и в первых трёх, и времени от начала сбоя до разбора. | 3 |
| FR-10 | Система должна обеспечивать сравнение своего разбора с базовым подходом «источник — сервис, чей триггер сработал первым» на одних и тех же размеченных сбоях. | 3 |
| FR-11 | Система должна предоставлять в интерфейсе Zabbix карточку инцидента: таймлайн отклонений по сервисам, графики метрик, доказательства из логов, список подозреваемых. | 3–4 |
| FR-12 | Система должна предоставлять в интерфейсе Zabbix страницу с результатами оценки точности разбора и сравнения с базовым подходом. | 4 |

## Если успеем

| ID | Требование | Идея |
|---|---|---|
| FR-13 | Система должна обеспечивать обнаружение аномального поведения сервиса моделью машинного обучения по группе его метрик и запись оценки аномальности в элемент Zabbix. | 22 |
| FR-14 | Система должна обеспечивать краткий пересказ разбора с помощью LLM с маскированием имён, адресов и секретов перед отправкой. | 3, 4 |
| FR-15 | Система должна обеспечивать отметку в Zabbix проблем-симптомов, чтобы оповещение приходило о причине, а не о каждом следствии. | 8 |
| FR-16 | Система должна обеспечивать поиск похожих прошлых инцидентов и показ того, что тогда помогло. | 10 |
| FR-17 | Система должна предоставлять инженеру оценку разбора («верно» / «неверно, причина в …») и учитывать её в точности. | 13 |

## Что изменилось по сравнению со спринтом 1
- **Сбор, хранение, триггеры** больше не делаем сами — это Zabbix (было FR-01, FR-03, FR-04, FR-05).
- **Генератор** заменён стендом [test-server](https://github.com/ITMO-DWS-Green/test-server) со сбоями по кнопке и разметкой (было FR-01, FR-02).
- **Своё веб-приложение** заменено модулем внутри интерфейса Zabbix (было FR-13).
- **Чат инцидента** — сообщение в групповой чат команды в Telegram: бот Telegram не может сам создавать группы ([D-006](../architecture/decisions.md)).
- **Два подхода** теперь сравниваются в разборе причины: наш разбор против «первого сработавшего триггера». ML — опционально (FR-13).
